# timesnow —— 设计愿景

一个用 Rust 写的视觉小说引擎。
叙事优先，现代渲染，库模式。

**贯穿五个维度的一条线：叙事是一等公民，但渲染不将就。**

这份文档回答五个问题。每个维度给出对照（别人怎么做）、我们的选择、
以及**现在做到哪一步**——有"现状"这一栏，它就不只是愿望清单。

## 一、视觉小说能做什么

**核心问题：这个引擎服务的"视觉小说"是什么样的？**

**Ren'Py 的答案：** 静态背景 + 静态立绘 + 文本框 + 分支选项。
这套模型用了二十年，成熟到几乎成了视觉小说的定义。

**timesnow 的答案：** 叙事优先，但渲染用现代 GPU。
目标不是复刻 Ren'Py 的表现力，而是**能做出 Ren'Py 原生做不到的视觉效果**——
实时立绘、动态场景、shader 驱动的风格、复杂状态管理。

**关键判断：** 这不是"更好的 Ren'Py"，是另一条路。
Ren'Py 把叙事做得很好，渲染上有限；timesnow 想在两者之间找平衡。

**现状：**

| 目标 | 现在有什么 | 缺什么 |
|---|---|---|
| 叙事基础设施 | 对话、立绘、背景、分支、变量与算术、存读档、回看历史、章节标签、热重载 | —— |
| 实时立绘 | 静态矩形 + tint | **动画系统**：关键帧、缓动、属性补间 |
| 动态场景 | 一个背景名 | 视差、多层滚动、环境动画 |
| shader 驱动的风格 | 一个 sprite shader（tint + alpha） | 材质/挂钩、后处理链 |
| 复杂状态管理 | 全局变量 + `@if` | 集合、状态机 |

**最后三行是这份文档里最大的空白。** 它们不是 shader 问题，
是三个还不存在的子系统。见[路线图](roadmap.md)。

## 二、谁来做视觉小说

**核心问题：这个引擎服务的是谁？**

**Ren'Py 的用户：** 不会写代码的编剧和画师。这是它的核心价值，也是它的设计前提。

**timesnow 的用户：** 会写代码的叙事创作者。

- 能写代码，也懂叙事
- 想做的不只是"静态立绘 + 文本框 + 分支"
- 在通用引擎里做视觉小说，基础设施要自己搭太累
- 想用的效果 Ren'Py 原生做不到

**关键判断：** 这个定位决定了后面所有设计——DSL 不需要面向完全不懂代码的人，
也不需要面向纯逻辑的程序员。

**一个更准的划法：** 这个群体**不是按职业分的，是按"愿不愿意为画面多花一点力气"分的**。
"会写代码的叙事创作者"听起来像是程序员和编剧的交集，
但真正的区分在维度一——他们想要 Ren'Py 给不了的效果。写不写代码只是手段。

具体一点：一个人想做一个三小时的悬疑短篇。分支多但结构要清楚，
存档得能标出"这是第几章"，有几段画面效果是 Ren'Py 里要绕才能做到的。
她不需要为对话框和存档界面写一两千行胶水代码，
也不需要在 Godot 里从零搭一套对话系统。

## 三、边界画在哪里

**核心问题：这个引擎只做视觉小说，还是能做别的？**

三种边界：

- **窄边界**：视觉小说引擎（Ren'Py 的路线）
- **宽边界**：叙事游戏引擎（timesnow 的路线）
- **无限边界**：通用游戏引擎（Bevy / Godot 的领域）

**timesnow 的选择：宽边界。** 叙事优先，但底层通用。

> 凡是叙事驱动的游戏，都能做，而且能做得比通用引擎省事。

架构上想分三层：

| 层 | 职责 | 现状 |
|---|---|---|
| 核心层（通用） | 渲染 / 资源 / 输入，不含视觉小说概念 | 渲染和资源有了；输入还在 `App` 里，没有抽象出来 |
| 叙事层（专注） | 对话、立绘、剧情推进、DSL | 最完整的一层 |
| 玩法层（插件） | 数值、卡牌、战斗等，开放接口 | **只有设想**：没有 `trait`、没有注册机制、没有回调点 |

组合起来的样子：

- 视觉小说 = 核心 + 叙事 + 默认 UI
- 叙事 RPG = 核心 + 叙事 + 战斗插件
- 恋爱模拟 = 核心 + 叙事 + 数值插件

后两个是方向，不是现状。

**关键判断：对外只说"视觉小说引擎"。宽边界是内部架构，不是宣传口径。
先把视觉小说做扎实，再看其他可能性。**

这条同时也是最危险的维度——"宽边界"可以给任何东西背书。
所以配了一份[刻意不做的事](#刻意不做的事)。

## 四、引擎和游戏的关系

**核心问题：引擎和游戏是什么关系？**

**Ren'Py 模式：** 一体化包。引擎包含游戏，你在它的目录里写脚本。

**Godot 模式：** 引擎 + 项目。编辑器打开项目，引擎是黑盒。

**timesnow 的选择：库模式。**

引擎是一组 crate，游戏是独立 cargo 项目，通过 `Cargo.toml` 依赖。

- 游戏可以独立版本控制
- 游戏可以独立发布（不附带引擎 SDK）
- 游戏可以独立升级引擎（改版本号）

**关于兼容性，把话说清楚：**

| 东西 | 承诺 |
|---|---|
| 存档格式 | **向后兼容**。有版本号和金标准测试兜住，老存档必须能读 |
| Rust API | **不保证**。早期项目，接口会随版本变 |
| DSL | **只加不删**。真要废弃，至少留一个大版本 |

"不破坏已有游戏"是个很强的承诺，而它不能靠愿望实现——
存档那边是靠版本号和回归测试换来的（v1 存档读不出来那个 bug 就是证据），
API 这边现在给不出同样的保证，所以不承诺。

配套双轨：

**轨道 A：库模式**（已经有了）——引擎是一组 crate，游戏是 Rust 项目，完全可定制。

**轨道 B：项目模式**（还没做）——一个 CLI 生成项目脚手架，
用户只写 DSL 和资源，不碰 Rust。目标是让不写 Rust 的人也能用同一个引擎核心。

**关键判断：引擎是工具，不是老板。用户可以精确控制引擎的每一个行为，
也可以完全不管引擎的内部。**

## 五、怎么用起来

**核心问题：用户每天面对的迭代循环是什么样的？**

**Ren'Py 的答案：** 改一行台词，立刻看到效果。这是它的杀手锏。

**Rust 的困境：** 编译慢。不可能跟 Ren'Py 比编译速度。

**timesnow 的答案：不是让编译器变快，而是让编译器不需要被调用。**

| 层 | 是否编译 |
|---|---|
| 内容层（剧本、配置、资源） | 不编译，运行时加载 |
| 逻辑层 | 不编译 Rust |
| 引擎层（Rust） | 编译，但很少改 |

**已经实现：**

- 剧本热重载（改 `script.tsn`，游戏里立刻生效）
- 配置热重载（改 `config.toml`，UI 立刻变）
- 资源自动注册（丢进 `assets/` 就能用，不需要清单文件）
- 无窗口校验（`--check`，CI 里跑，不需要显卡）
- 错误页 + 自动恢复（剧本写错不崩，改对了自动继续）
- 检查提示能指出正确的名字（`@coice` → "你是不是想写 `@choice`？"）

**下一步：**

- WASM 预览、多分辨率适配、剧情流程图

**更远（各自是一个产品）：**

- 可视化编辑器、插件体系与数据导出

**关键判断：这是决定引擎能不能留住用户的关键维度。
用户不会因为"支持 shader"迁移，但会因为"改一句话要等半分钟"离开。**

## 五个维度怎么咬合

它们不是并列的，是层层递进的：

```
一（做什么）    ——  定义产品形态
    ↓
二（服务谁）    ——  定义目标用户
    ↓
三（边界在哪）  ——  划定范围
    ↓
四（什么关系）  ——  定义工程结构
    ↓
五（怎么用）    ——  定义日常体验
```

一和二决定"这东西是给谁做什么"。三划定它到哪为止。四决定它在工程上怎么落地。
五决定用户每天用起来是什么感觉。

少了任何一条，它都会变成另一个东西：少了一就是"又一个 Ren'Py"；
少了二不知道服务谁；少了三变成什么都能塞；少了四变成一体化包；
少了五变成"能跑但没法用"。

## 刻意不做的事

边界说的是"到哪为止"，这一节说的是"明确不做"。
没有它，"宽边界"可以给任何东西背书。

- **不做通用游戏引擎。** 不做 3D、不做物理、不做网络、不做通用 UI 框架。
  这些是 Bevy / Godot 的领域，做了也做不过。
- **不做一体化编辑器。** 引擎是工具，不是 IDE。
  想要可视化编辑的话，那是另一个产品，而且是独立的产品。
- **不把 DSL 变成脚本语言。** 不嵌 Rhai / Lua / JS 进 `@if` / `@set`。
  超出 DSL 边界的东西下沉到别的层，不是塞进 DSL。
- **不为"看起来完整"堆特性。** 没人在用的功能也是要维护的。

## 怎么算成功

短期目标很具体：

> **我自己用它做完一部能拿出去给人玩的短篇。**

在那之前不加通用功能——不加插件体系、不加编辑器、不为了完整而完整。

这条不是自我限制，是排序的依据。上面列的那些"更远"的东西什么时候做，
取决于这部短篇做完之后我撞到了什么。到那时缺什么，比现在猜什么准。

**附带一条：** 这部短篇应当**用上至少一个 Ren'Py 做不到的效果**。
否则"渲染不将就"这个前提就没有被验证过——那是最坏的情况：
引擎长得像 Ren'Py，却没有 Ren'Py 的成熟度。

## 写在最后

我想做的是一个不同方向的视觉小说工具。

不是说它更好，只是说它不同。
Ren'Py 已经很好用了二十年，我不是来取代它的。
我只是想看看，用另一种思路，能做出什么。

这个方向可能走得通，也可能走不通。
但我想把它走一遍。
