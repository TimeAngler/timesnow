# timesnow —— 设计愿景

一个用 Rust 写的视觉小说引擎。
叙事优先，现代渲染，库模式。

## 为什么做这个

我做 timesnow，是因为我没有找到一个完全符合我需求的工具。

Ren'Py 的渲染模型是二十年前的设计，为那个时代的硬件和游戏形态服务。
它把叙事做得很好，但画面上的可能性有限。

Godot、Unity、Unreal 渲染能力很强，但它们把叙事当作附加系统，而不是核心。
用它们做视觉小说，对话系统、立绘管理、剧情推进都要从零搭。

我想试一条不同的路：

> 一个既把叙事当作一等公民、又能用上现代 GPU 的引擎。

这不是在说哪条路更好。只是说，我想走这条。

## 它服务谁

主要用户是：**会写代码的叙事创作者**。

- 能写代码，也懂叙事
- 想做的不只是"静态立绘 + 文本框 + 分支"
- 在通用引擎里做视觉小说，觉得基础设施要自己搭太累
- 想用的效果 Ren'Py 原生做不到

这不是"程序员"，也不是"纯编剧"，是两者之间的那批人。

具体一点：一个人想做一个三小时的悬疑短篇。分支多但结构要清楚，
存档得能标出"这是第几章"，有几段画面效果是 Ren'Py 里要绕才能做到的。
她不需要为对话框和存档界面写一两千行胶水代码，也不需要在
Godot 里从零搭一套对话系统。

对这个群体，我在意的几件事：

1. 叙事基础设施是原生的（对话、立绘、剧情推进、资源管线）
2. 渲染层开放，但不需要从零搭
3. 脚本层可以分层（DSL 写剧情，Rust 写逻辑）
4. 开发体验要快（热重载、实时预览）
5. 扩展性像 Godot（插件、自定义、数据导出）

**第 5 条现在还是空的。** 没有插件接口，也没有数据导出。
前四条的进展不一样，后面分开说。

## 现代渲染意味着什么

这是三个支柱里最需要展开的一个，因为它正是"为什么不用 Ren'Py"的答案。

**做过的事：**

- 渲染层直接建在 wgpu 上，不是套在别人的渲染器外面
- 立绘、背景、UI 都是实例化的四边形，一层层叠上去
- tint 走 shader 里的一个分量：铺一张白纹理加 tint 就等于纯色块
- 全局 alpha 一条通道走通，淡入淡出不碰各层自己的状态
- 文字用 glyphon，带按内容缓存的排版
- 没有动画时事件循环进 Wait——静止画面的 CPU 占用接近零

**这些带来什么：** 当你想做 Ren'Py 里要绕的效果时，**底下是 shader 和图层，不是一台需要绕过去的机器**。
想要角色被光照影响、想要整屏色调随剧情变化、想要自定义转场——
改 shader 或者加一个新的渲染 pass，而不是找有没有现成的 API。

**代价是什么：** 这条路更难走。如果你只想做"静态立绘 + 文本框 + 分支"，
Ren'Py 今天就能用，而且做得比我好。timesnow 是给愿意为画面多花一点力气的人准备的。

## 引擎和游戏的关系

我选择**库模式**。

引擎是一组 crate，游戏是独立 cargo 项目。通过 `Cargo.toml` 依赖。

这意味着：

- 游戏可以独立版本控制
- 游戏可以独立发布（不附带引擎 SDK）
- 游戏可以独立升级引擎（改版本号）

**关于兼容性，我把话说清楚：**

| 东西 | 承诺 |
|---|---|
| 存档格式 | **向后兼容**。有版本号和金标准测试兜住，老存档要能读 |
| Rust API | **不保证**。早期项目，接口会随版本变 |

"不破坏已有游戏"是个很强的承诺，而它不能靠愿望实现——
存档那边是靠版本号和回归测试换来的，API 这边现在给不出同样的保证。

配套想做的两轨：

**轨道 A：库模式**（已经有了）

引擎是一组 crate，游戏是 Rust 项目。
完全控制，完全可定制。

**轨道 B：项目模式**（还没做）

一个 CLI 生成项目脚手架，用户只写 DSL 和资源，不碰 Rust。
目标是让不写 Rust 的人也能上手同一个引擎核心。

两条轨道共享同一个引擎核心。

## 开发体验

这是决定引擎能不能留住用户的关键。

Rust 编译慢。我不打算跟谁比编译速度。
解决方案不是让编译器变快，而是让它不需要被调用。

分层：

| 层 | 是否编译 |
|---|---|
| 内容层（剧本、配置、资源） | 不编译，运行时加载 |
| 逻辑层 | 不编译 Rust |
| 引擎层（Rust） | 编译，但很少改 |

**已经实现：**

- 剧本热重载（改 `script.tsn`，游戏里立刻生效）
- 配置热重载（改 `config.toml`，UI 立刻变）
- 资源自动注册（丢进 `assets/` 就能用，不需要清单文件）
- 无窗口校验模式（`--check`，CI 里跑，不需要显卡）
- 错误页 + 自动恢复（剧本写错不会崩，改对了自动继续）

**下一步（同一量级，做得到）：**

- WASM 预览
- 多分辨率适配工具
- 剧情流程图（哪些块通向哪些结局）

**更远（各自是一个产品）：**

- 可视化编辑器
- 插件体系与数据导出

把自己想要的和需要一整个产品才能做完的分开列，
免得后者把前者的进展盖住。

## 设计的边界

三种边界：

- **窄边界**：视觉小说引擎
- **宽边界**：叙事游戏引擎
- **无限边界**：通用游戏引擎

我选**宽边界**：叙事优先，但底层通用。

> 凡是叙事驱动的游戏，都能做，而且能做得比通用引擎省事。

架构上想分成三层：

| 层 | 职责 | 现状 |
|---|---|---|
| 核心层（通用） | 渲染 / 资源 / 输入，不含视觉小说概念 | 渲染和资源有了，输入还在 `App` 里 |
| 叙事层（专注） | 对话、立绘、剧情推进、DSL | 这一层最完整 |
| 玩法层（插件） | 数值、卡牌、战斗等，开放接口 | **只有设想，没有接口** |

组合起来的样子：

- 视觉小说 = 核心 + 叙事 + 默认 UI
- 叙事 RPG = 核心 + 叙事 + 战斗插件
- 恋爱模拟 = 核心 + 叙事 + 数值插件

后两个是方向，不是现状。**玩法层现在没有 `trait`、没有注册机制、没有回调点**——
要做它，得先想清楚插件能碰什么、不能碰什么，以及它怎么和存档格式共存。

## 关于 DSL 的定位

这条单独列出来，因为它是个明确的选择。

timesnow 的 DSL 是：

> **剧本语言**

不是：

> ~~脚本语言~~

这意味着：

- DSL 为叙事服务，不为编程服务
- 简单的事情简单，复杂的事情可能
- DSL 的边界是"视觉小说的常见模式"
- 超出边界的东西，下沉到别的层，不是塞进 DSL

具体的选择：

- 不把 Rhai / Lua / JS 嵌进 `@if` / `@set`
- 不让 DSL 变成"带剧本语法的脚本语言"
- 不让 DSL 变成一个需要配调试器的东西

层次划分：

| 层 | 用途 | 面向 |
|---|---|---|
| DSL | 写剧本 | 90% 的用法 |
| Rust 插件 | 扩展引擎 | 少数高级用户 |
| 脚本层 | 复杂逻辑 | 独立文件，不是嵌在 DSL 里 |

叙事和逻辑是两个东西。我让它们各自有各自的位置。

保持 DSL 专注。

## 现状

早期项目。API 会变。欢迎试用和反馈。

已经能跑通一个完整的短篇视觉小说：
从标题画面到分支结局，有立绘、BGM、存读档界面、回看历史、热重载。

存档格式向后兼容是老存档的底线；
Rust API 和玩法层接口都还在动。

## 怎么算成功

短期目标很具体：

> **我自己用它做完一部能拿出去给人玩的短篇。**

在那之前不加通用功能——不加插件体系、不加编辑器、不为了"看起来完整"而堆特性。

这条不是自我限制，是排序的依据。上面列的那些"更远"的东西什么时候做，
取决于这部短篇做完之后我撞到了什么。到那时缺什么，比现在猜什么准。

## 写在最后

我想做的是一个不同方向的视觉小说工具。

不是说它更好，只是说它不同。
Ren'Py 已经很好用了二十年，我不是来取代它的。
我只是想看看，用另一种思路，能做出什么。

这个方向可能走得通，也可能走不通。
但我想把它走一遍。
