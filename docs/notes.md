# 设计笔记

**这份是给我自己看的。**

[设计愿景](vision.md) 是对外的：它讲 timesnow 是什么。
[路线图](roadmap.md) 是清单：它讲接下来做什么。

**这份讲"为什么"，以及"当时的判断错在哪"。**

为什么单独写一份：结论会过期，推理不会。
半年后再看"阶段 1 排第一"，如果不知道为什么，就只能凭感觉改。
而这份里全是推理——以及**被证伪的记录**。

---

## 一、路线图为什么这么排

### 排序依据不是"哪个简单"，是"哪个前提还没被验证"

我一开始列过一份"引擎还缺什么"的清单：动画、后处理、插件、脚手架、
WASM、编辑器、流程图、存档缩略图……十几个。

**那份清单没用**，因为它没排序依据——为什么先做插件而不是后处理？说不上来。

真正的依据来自愿景里那句话：

> 叙事优先，但渲染不将就。

拆开看：

- **叙事优先** —— 已经做到了。对话、分支、变量与算术、存读档、回看历史、
  章节标签、热重载，一层一层都全，而且有 253 项测试钉住
- **渲染不将就** —— **一个都还没有。** 渲染层没有 tween、没有缓动、
  没有后处理，DSL 没有集合类型

而引擎存在的**理由**恰恰是后者。"为什么不用 Ren'Py"的答案不是
"我的存档做得更好"，是"Ren'Py 给不了的效果我能给"。

**所以：这个前提还没被验证过一次。而它没被验证，其他所有东西的优先级
都无从谈起。**

### 阶段 0 和阶段 1 必须咬合——我推翻了自己一半

我前面几轮一直在说"先去做完一部短篇"。写路线图时我发现**这话只说对了一半**：

**做完 `phone` 验证不了这个引擎的价值。** 它验证的是叙事层——
而叙事层是唯一已经完整的一层。

最坏的结果是：一部短篇做完了，引擎长得像 Ren'Py，
却没有 Ren'Py 的成熟度（人家二十年，有生之年追不上）。

所以阶段 0 的完成标志我加了后半句：

> 至少用上**一个 Ren'Py 做不到的效果**。

这一句让两个阶段咬在一起，**你没法只做其中一个**。

那为什么不干脆跳过阶段 0 直接做动画？
因为**没人从头玩到尾，就不知道它到底缺什么**。

### 阶段 0 的真实作用是当探针

我保留阶段 0 不是因为"该有个作品"，是因为它的**信息价值**。
前面几轮的证据非常一致：真实数据抓出来的问题，测试抓不到。

| 问题 | 谁抓到的 |
|---|---|
| v1 存档全部读不出来 | 一份真实的历史存档文件。**当时 242 项测试全绿** |
| 设置界面行叠字 | 你截图 |
| 跳过功能等于没跳过 | 你实跑 |
| `@quit` 不生效 | 实跑（而且我第一次验证时还搞错了工作目录） |

**每一次都是我"验证过了"而实际没验到。** 所以阶段 0 是探针，不是里程碑。

### 阶段 1 的关键发现：它比看上去便宜

写路线图时我**先核实了一件事**，结果改变了我对工作量的判断。

我原本以为"实时立绘"要重写渲染器。核实之后：

| 需要什么 | 有没有 |
|---|---|
| 每帧喂立绘位置 | ✅ `set_characters(&[(name, Rect)])` |
| 每帧驱动钩子 | ✅ `Script::update(dt)`，和打字机、`@fade` 共用 |
| 要补间的字段 | ✅ `StageRect { x, y, w, h }` |
| 透明度和着色 | ✅ 全局 alpha + shader 的 tint 分量 |
| 纯函数测试 | ✅ 渲染层有 21 项 |

**所以动画是加在现成结构上的一个纯数值模块，不是重写渲染器。**
这把它从"很大的工程"变成三个能写清完成标准的任务。

### 1.1 补间引擎为什么排最前：因为它是纯的

- 不碰 GPU、不碰窗口、**时间由调用方传进来**（和 `Vm` 同一条设计线）
- 意味着动画最容易出的错**全都能在单测里钉住**：
  - 缓动在 `t=0` / `t=1` 差一点点（浮点累积误差）
  - 时长 0 卡住（`@fade to 0.0 0.0` 已经卡过一次，同一个坑）
  - 关键帧无序
- 不用等画到屏幕上才发现

**这是这个引擎一直在用的办法**：把纯逻辑抽出来、先测透，再接进有副作用的层。
渲染层的 21 项测试、`vm.rs` 的独立、`ui_metrics` 的抽出，都是同一个动作。

### 阶段 2 为什么明确写"不建议提前做"

骨骼形变、后处理链、状态管理——这三项**看起来**才是"现代 GPU"该有的样子，
很容易让人想直接冲。我把它排后并写了一句硬话：

> 没有真实需求的话，做出来的接口大概率是错的。

这不是保守，是具体判断：**这三项不是难在实现，是难在接口设计。**
"作者怎么写、引擎怎么理解"——这两个问题的答案只能从**用过动画之后**
的反馈里来。

现在设计骨骼接口，等于凭空想象作者会怎么控制角色的呼吸。

### 阶段 3 为什么排最后

WASM、脚手架、插件、编辑器是"**让别人也能用**"的东西。
**引擎本身还没好用到值得别人用。** 先做等于给半成品做包装。

其中一个有隐藏难度，我在路线图里单独标了：**插件接口**。
它要回答"插件能碰什么、不能碰什么，以及**它怎么和存档格式共存**"。

最后那半句是真问题。存档模型是"结构指纹 + 游标"，
插件一旦能改剧本状态，那个模型就要重新想——
这不是加个 `trait` 的事。

### 整个规划里唯一真正的设计难题

路线图里其他条目都是"怎么做"，只有一个是"**做成什么样**"：

> **存档时正好有一个播到一半的动画，存什么？**

- **存终态** —— 读档后画面是"完成的样子"，动画从头播一遍
- **存当前值** —— 读档后停在半路

我倾向**存终态**，理由是"可预期"：玩家读档后该看到稳定的画面，
不是某个卡住的中间帧。

**但这个决定得我拍**，因为它影响的是"玩家对存档的直觉"，不是技术问题。
而且它一旦定了，会反过来约束 `@move` 的 DSL 写法。

## 二、我没做的三件事

**1. 没排时间。** "阶段 1 大约两周"这种话写不出来——不是谦虚，是真不知道。
而且已经被证明过一次：跳过功能"逻辑完全正确"，体感等于没跳。
**排时间会给一个假的安全感。**

**2. 没排版本号。** 哪个阶段进 v0.2、哪个进 v0.5，取决于阶段 0 撞到什么。
现在定就是猜。

**3. 没删"更远"的东西。** 可视化编辑器留在阶段 3，但标了
"**独立产品，不是这个引擎的一个功能**"——把它和"WASM 预览"并列，
会稀释前面那些真进展。

## 三、我在这个项目上判断错的记录

**这一节是这份文档存在的主要理由。**

留着的用处：下次我又很确定某件事的时候，可以回来看看我的命中率。

| 我说的 | 实际 | 怎么发现的 |
|---|---|---|
| "未知指令什么都不说" | 已经在报错，而且很准（`@coice`、`@wait` 少参数、变量拼错、块名拼错、资源拼错都有） | 实测 |
| "`phone` 里 `title` 是死块，标题画面可能看不到" | 假警报——我的检查脚本按文件系统顺序拼块，不等于 `include` 顺序 | 去读 `script.tsn` |
| "② 存档金标准测试是防未来" | **它抓到了当前一个致命 bug**：`Value` 改成 untagged 之后所有 v1 存档读不出来 | 测试第一次运行就红 |
| "引擎 6736 行" | 口径算错 | 重新量 |
| "`@set` 不能算数是设计缺陷" | 是取舍，而且可以补（已补，且没破坏存档模型） | 实现的时候 |
| "这个引擎已经够做短篇了" | 叙事层够了，**但引擎存在的理由一项都没验证** | 写路线图时核实 |

**规律：我持续低估这套代码，同时高估自己的判断。**

对这段记录的操作性结论只有一条：
**任何"我验证过了"的话，都要问清楚验的是哪一层。**
（"夹具能被反序列化" ≠ "读档路径通了"，这两个我混淆过。）

## 四、几个我反复回来的判断

这几条是十几轮里没被推翻的，所以可信度高一些。

### 存档模型是这个项目最值钱的东西

指纹只看结构（块名 + 步数 + step 类型），所以**改台词不会让老档失效**。
Ren'Py 用 pickle 存整个对象图，文档里明确写"存档兼容性不保证"，
还有一节叫 "What Ren'Py Can't Save"。

**这不是抄来的，是主动选的。** 代价是 DSL 不能乱加东西——
而这个代价后来证明没有想象中大（算术和浮点补上之后，存档模型一个字节没改）。

**结论：以后加功能时，先问"它会不会污染存档模型"。**

### 零依赖增长应该继续

加了 backlog、9 槽存读档、设置界面、着色、算术、`@chapter`、`@quit`/`@title`、
建议系统、金标准测试——依赖从 12 个变成 10 个（删了 `rhai`）。

- 没引 chrono（自己拆时间）
- 没引 Pillow（自己写 PNG 字节）
- 没引编辑距离库（自己写 20 行）
- 没引状态机库（`Vm` 就是一个 `loop` 加 `match`）

**在这个圈子里这是很少见的自制力，也是这套代码体积小的原因。**

### 纯逻辑抽出来、先测透，是这个项目的核心手法

- `Vm` 从 `script.rs` 抽出来独立成 `vm.rs`（354 行）
- 渲染层的 `instance_transform` / `box_metrics` / `frame_quads` / `FrameGuard`
- `ui_metrics` 从 `draw_*` 里抽出来
- `suggest.rs` 的编辑距离

**每一次抽出来之后，都立刻抓到了东西。**
第 2 条抽完之后抓到了三个 UI bug；`FrameGuard` 抽出来之后
"一帧渲染两次"变成了可测的。

**结论：想不清楚怎么测，往往是因为形状没抽对，而不是因为不可测。**

### DSL 的边界是"剧本语言"不是"脚本语言"

不嵌 Rhai / Lua / JS。超出边界的东西下沉到别的层。

**这条在聊 Rhai 那轮定下来的，而且定得对**：
算术和浮点补上之后，DSL 对叙事作者的价值已经兑现了；
而循环、数组、函数那些——真需要的时候再说，
而且那时候会知道需要的是哪几个，不是笼统的"一门语言"。

## 五、还没验证的（我评估的最大盲区）

这些不是"可能有问题"，是**我确实没测过**：

- **8 小时游戏的内存曲线**。只测过几分钟的空闲 CPU（1–2% 单核）
- **几百个资源的加载时间和显存占用**
- **字体回退**：日文假名、阿拉伯文、emoji。现在只做到"提示用户装字体"
- **视觉效果和手感**。沙箱里开不了截图、注入不了按键。
  所有 UI 相关的 bug 都是你跑出来的
- **`script.rs` 还是 1805 行**。拆过一次（`vm.rs`），门面仍然最大
- **插件接口和存档模型怎么共存**。这是阶段 3 的真问题，现在没有答案

## 六、当前该做什么

**阶段 0 + 阶段 1 咬合做。**

具体下一步：**补间引擎（1.1）**。理由是它是纯函数、能完全单测，

**但更重要的是：做完之后要拿真实的东西去撞它。**

## 更新这份文档的规矩

**只在两种情况下改它：**

1. **判断被证伪了** → 加一行到第三节的表格里，**不要删旧的**
2. **定下了新的设计决定** → 加一节，写清楚"为什么"和"放弃了什么"

不要把它改成"项目进展记录"——那是路线图的活。
这份文档只有价值在**推理和错误**，不在结论。
